Custom Real-Time Rendering Engine

C++ / HLSL — Independent Graphics Programming Architecture
2nd September 2026
C++ DirectX 11 HLSL Render Graph PBR Metallic-Roughness PCF Shadows Assimp & GLTF

Developed from first principles to understand the underlying mathematics and architecture behind modern real-time rendering pipelines rather than relying entirely on game-engine abstractions. The engine began with rendering a basic triangle and progressively evolved into a full real-time renderer.

Pipeline Architecture & Development Flow
Triangle Rasterization → Dynamic Scene Manipulation → Texture Mapping → Assimp Asset Importing → Custom Transform System → First-Person Controller → Lambertian Shading → GLTF PBR Shading → Alpha Blending → Render Queue → Render Graph → Shadow Mapping (PCF) → Point-Light Cubemap → Skybox & Final Composite
Engineering Decisions
  • Direct Hardware Management: Built the pipeline without high-level engine wrappers, directly managing rendering passes, GPU resources, constant buffers, and pipeline states.
  • Render Graph Architecture: Replaced sequential rendering with a directed Render Graph coordinating frame clearing, shadow passes, lighting, object highlighting, and composition.
  • Rigorous Transform Math: Custom transform system supporting Euler/quaternion rotation, local/world hierarchy, and inverse transformations.
  • Physically Based Shading: Implemented PBR metallic-roughness shading matching GLTF material specifications.
  • Shadow Stability: Hardware Percentage Closer Filtering (PCF) and slope-scaled depth bias to eliminate shadow acne and Peter Panning.
  • Frustum & Debugging Tools: Built camera projection frustum visualization, scene object debuggers, and runtime performance counters.
Retrospective & Core Learning

Working from a triangle upward provided an intimate understanding of how scene data translates into screen pixels—from vertex streams and camera projections to GPU buffers, rasterization, lighting, shadow maps, and composition.
Core Principle: The more of the underlying system you understand, the less dependent you become on the abstraction built on top of it.

// SYS_ID: SIMULATION-01 // UNREAL ENGINE 5

Leonids — Data-Driven Ballistics System (Unreal Engine)

UWorldSubsystem • Parallel Tasks • Niagara Data Channels
2nd August 2026
Unreal Engine 5 UWorldSubsystem Parallel Task Execution Predictive Swept Collision Niagara Data Channel ~50,000 Spawns/Sec
The Problem

Traditional projectile implementations in Unreal Engine represent each projectile as an individual AActor with its own Transform, collision state, movement component, and tick function. In projectile-heavy combat involving rapid-fire weapons, Actor lifecycle overhead and collision queries quickly saturate the game thread.

The Architectural Solution

Instead of representing projectiles as Actors, Leonids treats projectiles purely as data managed centrally by a UWorldSubsystem. The subsystem maintains projectile state inside compact parallel arrays (position, velocity, damage, lifetime, rendering indices). Weapons submit spawn requests via a Blueprint-callable interface without owning projectile objects.

Multi-Stage Simulation Pipeline
1. Ballistic Integration → 2. Predictive Swept Collision → 3. Parallel Worker Tasks → 4. Deferred Event Dispatch → 5. Niagara GPU Visualization → 6. Fly-by Audio Tagging
  • Ballistic Trajectory Equation: Explicit ballistic integration with gravity: displacement = velocity × Δt + ½ × gravity × Δt², ensuring continuous curved collision trajectories rather than straight segment approximations.
  • Predictive Swept Collision: Queries geometry from current position toward predicted position, completely preventing high-velocity tunneling.
  • Thread Safety: Parallel simulation isolates workers from unsafe shared gameplay calls. Workers write into task contexts; events (damage, decals, sounds) are deferred and dispatched on the game thread.
  • Niagara Visualization: Bypasses Actor components entirely by streaming projectile transforms directly to GPU particle buffers via Niagara Data Channels.
  • Stress Benchmark: Stress-tested at ~50,000 projectile spawns per second with predictable, deterministic memory consumption.
// SYS_ID: ARCH-01 // UNREAL ENGINE 5

Unreal Async Asset Streaming Framework

Soft Object References • Logical Actor Separation • Open-World Ready
Ongoing Framework
Soft Object References Asynchronous Loading Memory Footprint Reduction < 200 KB Logical Residency
The Problem

During gameplay prototyping, weapon actors, pickups, and interactables loaded their meshes, textures, materials, and physics data immediately on level initialization. In large or open-world maps, loading fully initialized actors saturates memory and causes frame stutters, even when 95% of those assets are far outside the player's immediate view.

The Architectural Solution

Redesigned the asset pipeline around Soft Object References. Gameplay objects initially exist strictly as lightweight logical entities. During construction, heavy visual references are cleared, leaving only gameplay logic in parent classes.

  • Once a player enters an activation range, the framework asynchronously streams only the required meshes before activating physics and rendering.
  • Pickups do not carry weapon visual assets; they designate weapon IDs and delegate mesh streaming to the player's weapon component.
  • Parent gameplay classes occupy under 200 KB in memory, remaining resident while heavy assets stream in and out dynamically.
  • Significantly improves casting and query performance, decoupling gameplay behavior (interaction, inventory, AI) from render state.

Janus — Modular Interaction Framework (UE5)

Actor Components • Data Tables • Soft References • State Machine
Active Architecture
Actor Components Data Tables Enum State Machine Loose Coupling

Gameplay interactions are among the most repeated systems in games. Traditional implementations result in duplicate interaction logic, hardcoded prompt strings, and conflicting animation hooks across every interactable object in the game.

  • Composition over Inheritance: Every interactable derives from a base BPC_Interact component, extended for pickups, NPC dialogues, world switches, and doors.
  • Data-Driven Definitions: Interaction types and prompt data are configured in Unreal Engine Data Tables with enums (Interact, Talk, Pickup, Open, Close), removing hardcoded script dependencies.
  • Asset Streaming Integration: Leverages Soft Object References so interactables remain lightweight until player proximity triggers asset loading.
  • Event-Driven Reaction: Completed interactions communicate through an event messaging subsystem, allowing UI, audio, AI, and quest managers to react independently.

// SYS_ID: SIMULATION-02 // UNITY DOTS

Leonids — Data-Driven Ballistics System (Unity)

DOTS • Burst Compiler • Job System • Structure of Arrays
24th January 2026
Unity DOTS Burst Compiler Job System RaycastCommand Batching 1,000,000 Projectiles/Frame
The Problem

Unity GameObject bullet architectures suffer from an $O(n)$ main-thread update loop. Even with pooling, active bullets invoke individual Update() ticks, incurring massive cache misses and managed overhead.

The Architectural Solution

Eliminated GameObjects entirely. Preallocates a fixed-size NativeArray<ProjectileData> capable of simulating up to 1,000,000 projectiles simultaneously. Insertion is handled via an $O(1)$ rolling index allocator.

  • Structure of Arrays (SoA): Data is aligned in SoA layout to maximize CPU L1/L2 cache line hits, achieving a 30% performance boost over Array of Structures (AoS).
  • Burst-Compiled Multithreading: Projectile simulation runs across all available CPU threads with SIMD vectorization.
  • Asynchronous Raycasting: Raycasts are generated into continuous buffers and evaluated via RaycastCommand.ScheduleBatch.
  • Direct GPU Consumption: Collision results write to a thread-safe queue, while projectile position buffers are bound directly to URP draw passes, Compute Shaders, or VFX Graph with zero CPU GameObject transform syncing.

Atlas — Open-World Streaming Framework (Unity)

Unity Addressables • 1000m Chunk Partitioning • Tested on GTA San Andreas Map
Late 2026
Unity Addressables Chunk Partitioning Adaptive Probe Volumes ~200 FPS on 4GB VRAM

Chunk-based asynchronous streaming framework built on Unity Addressables. The world is partitioned into 1000 × 1000 meter streaming regions. As the player traverses the environment, Atlas continuously monitors player coordinates and loads only the 3 × 3 active chunk neighborhood, unloading distant chunks asynchronously.

  • Dynamic GI Without Baked Lightmaps: Designed for open-world dynamic lighting, utilizing Unity's Adaptive Probe Volumes (APV) and light scenarios to eliminate massive static lightmap memory.
